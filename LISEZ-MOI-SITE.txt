Mettre en ligne sur Hostinger
-----------------------------
Le site actuel est un Hostinger Website Builder. Il faut le remplacer par ces fichiers.

1. hPanel → Sites web → martinlisen.com → dans le menu du site, supprimer (ou
   « détacher ») le Website Builder du domaine. Hostinger propose alors de gérer
   le domaine avec un hébergement web classique.
2. hPanel → Hébergement → martinlisen.com → Gestionnaire de fichiers → public_html.
   Vider ce dossier (garder une copie si tu veux), puis déposer TOUT le contenu de
   Site_martinlisen/ (les fichiers .html, .htaccess, robots.txt, sitemap.xml et le
   dossier assets/). Le dossier Sources/ n'est pas nécessaire en ligne, mais ne gêne pas.
   Le dépôt se fait par glisser-déposer dans le Gestionnaire de fichiers, ou par FTP
   (identifiants dans hPanel → Fichiers → Comptes FTP).
3. Vérifier que l'index est bien index.html (hPanel → Avancé → Index du site, si proposé)
   et que le certificat SSL est actif (hPanel → Sécurité → SSL). Forcer le HTTPS.
4. Ouvrir https://martinlisen.com, https://martinlisen.com/labs.html et une URL
   inexistante (doit afficher la page 404 du site).

Variante recommandée : déploiement par Git (le site vit sur GitHub, Hostinger le clone)
1. Supprimer ou détacher le Website Builder, comme ci-dessus, pour que public_html soit vide.
2. hPanel → Sites web → martinlisen.com → Avancé → Git → dépôt
   https://github.com/nftmooods/Site-web, branche main, répertoire vide (= public_html) → Créer → Déployer.
3. Activer le déploiement automatique si proposé : chaque push sur main met le site à jour.

Variante : si tu préfères garder le Website Builder actif le temps de vérifier,
dépose le site dans un sous-domaine (ex. nouveau.martinlisen.com) puis bascule.

Modifier le site
----------------
Chaque page est un fichier .html complet : on peut corriger un texte directement dedans.

Pour éviter que l'en-tête et le pied de page divergent entre les pages, ils sont aussi
dans Sources/parts/ et le contenu de chaque page dans Sources/pages/. Après une
modification dans Sources/, regénérer les pages :

    python3 Sources/build-site.py

Règle : corriger à la source (Sources/), jamais seulement dans le fichier généré.

Après chaque modification de site.css ou site.js, relancer build-site.py : il ajoute une
empreinte du fichier dans les liens (site.css?v=...), ce qui force les navigateurs à
recharger la nouvelle version au lieu de garder l'ancienne en cache. Si le site en ligne
semble ne pas refléter une mise à jour, c'est presque toujours ça : vérifier que le build a
tourné, puis vider le cache Hostinger (hPanel → Avancé → Cache).
Si tu modifies un fichier .html à la racine sans passer par Sources/, la prochaine
regénération écrasera ta modification.

Les couleurs, typographies et rayons sont en tête de assets/css/site.css (:root).

Statistiques de visite (Umami)
------------------------------
Umami tourne sur le VPS (Coolify). Pour l'activer sur ce site :
1. Dans Umami : Settings → Websites → Add website → Name « martinlisen.com »,
   Domain « martinlisen.com » → Save. Puis Edit → Tracking code : noter l'adresse du
   script (https://…/script.js) et le Website ID.
2. Coller ces deux valeurs en tête de Sources/build-site.py (UMAMI_SCRIPT, UMAMI_WEBSITE_ID).
3. Relancer python3 Sources/build-site.py, commiter, pousser sur main.
Le script est chargé en « defer » et limité au domaine martinlisen.com (les aperçus locaux
ne comptent pas). Umami ne pose aucun cookie : la mention du pied de page passe alors à
« statistiques anonymes, auto-hébergées ». Tant que les deux valeurs sont vides, rien
n'est ajouté aux pages.

Règles éditoriales tenues sur ce site
-------------------------------------
- Le texte est tourné vers le lecteur (tutoiement partout, y compris pour les équipes :
  « ton équipe », pas « votre équipe »), sa situation, son problème. Accroches et pitchs
  parlent de ce que le lecteur vit et récupère ; le « je » reste réservé aux preuves vécues
  et à la bio (section « Qui est derrière »).
  Fil de l'accueil : tes essais IA d'aujourd'hui → des méthodes et outils utiles au quotidien
  (explorer, construire, utiliser).
- En façade : « Strates Digitales » + libellés plats (le média, le Lab, les ateliers,
  les formations, le podcast, l'accompagnement). Pas de Strate 0, de codes 0x01, de
  Stratagème ni de Stratège : c'est la taxonomie interne Notion.
- Un seul appel à l'action de contact, toujours le même libellé : « On en parle ? »
  (Calendly), dans le menu du haut et dans le bloc final de chaque page. Ne pas multiplier
  les variantes (« Parlons de… », « Réserver… »). Le média et le Lab renvoient vers
  « Travailler avec moi ».
- Le Lab : un outil en vente porte son lien d'achat (Crumble Toolkit → Superhive). Un outil
  en usage ou une piste renvoie vers « Travailler avec moi ».
- Les fiches de l'accueil et des formations disent honnêtement où en est chaque chose :
  « existe déjà » (outil, formation) ou « à construire ensemble ». À respecter à chaque ajout.
- Chiffres : uniquement ceux communiqués par Martin. Aucun chiffre inventé, arrondi
  seulement à la baisse. Ils apparaissent à deux endroits, à garder identiques :
    · accueil, sous le premier écran (bandeau discret « hero-stats ») : 500+ professionnels
      formés en présentiel, près de 30 000 cours suivis en e-learning (LinkedIn Learning), 100+ addons Blender vendus ;
    · accueil, section « Des outils créés. Des savoir-faire transmis. » (id #chiffres, le
      bandeau y renvoie) : les cinq chiffres complets avec leurs notes.
  Les 29 996 sont un nombre de COURS SUIVIS (somme des compteurs de sept cours LinkedIn Learning), pas de personnes : une
  même personne peut être comptée plusieurs fois. Ne jamais écrire « apprenants » ni « personnes » ; la
  note de bas de section doit rester. Si un chiffre change, le modifier aux deux endroits.
- Question laissée ouverte (Plan de démarrage, 20/09) : sur une fiche produit en vente,
  ajouter ou non un second lien discret « besoin d'un outil sur mesure → Travailler avec
  moi ». Pour l'instant : non, un seul lien d'achat.
